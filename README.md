# Finance Procurement Assistant

Ask questions about 2025 invoices and the procurement policy, and see exactly what each answer is
based on. FastAPI backend, React frontend.

**LLM path:** this was built and run in **stub mode**, clearly labelled in the API and UI. 

## Setup

Requires Python 3.11+ and Node 20+.

```bash
# Terminal 1: backend, http://localhost:8000
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --port 8000

# Terminal 2: frontend, http://localhost:5173
cd frontend
npm install
npm run dev
```

**Recommended: get exact FX rates.** Run `python backend/scripts/fetch_ecb_rates.py` and restart the
backend. Until then, EUR figures use 2025 annual-average ECB rates and are labelled indicative. The
script needs access to ecb.europa.eu; its parser is tested, but it has not run against the live file.

**Use a real model:** set the variables from `.env.example` in your shell before starting the backend.
**Tests:** `cd backend && python -m pytest`

## How it works

```
question -> PLAN (LLM or stub): route = data | policy | both | none, plus tool calls and clauses
         -> validate the plan (retry once)
         -> EXECUTE typed, read-only tools: all arithmetic and thresholds happen in code
         -> COMPOSE (LLM or template): prose only, from the evidence
         -> CHECK figures, invoice ids and citations (retry once, then use the template)
         -> respond with answer, route, evidence, caveats and provenance; write the audit log
```

Key decisions:

- **The model never calculates.** It chooses tool parameters and writes prose. Typed tools are used
  instead of text-to-SQL because they are safe by construction and easy to audit.
- **Evidence comes from code, not the model.** Clause quotes are looked up verbatim from the policy
  file, and every data row carries its CSV line number. Caveats are generated by code, so the model
  can't drop them.
- **Failures are visible.** An LLM outage returns a retryable 503 and never silently switches to the
  stub. If the model fails after the tools have run, the analyst gets the computed answer, labelled.
- **Approval bands are parsed from the policy table**, so the policy remains the single source of truth.

Data decisions that change the numbers:

| Issue | Decision |
|---|---|
| Three currencies, no FX rates in the pack | Convert per §5.1 and never sum native amounts. Daily ECB rates when fetched, otherwise annual average and labelled. |
| Non-publishing days (32 invoices fall on weekends) | Use the last published ECB rate. §5.1 does not cover this, so Finance should confirm it. |
| Two credit notes | "Spend" is net of credit notes; gross is also reported. |
| Non-compliant invoices | Kept in spend, because they were invoiced, but flagged next to the figure. |
| No role, requester, payment or credit-note link fields | Those controls are reported as `cannot_verify`, never as a pass. |

## Write-up

**What I built and left out.** I prioritised grounding and traceability, because in a controls setting
a wrong figure that looks authoritative is the worst outcome. The one optional extra is **agentic
routing**: it is the core of the LLM design, and the route and reasoning are shown on each answer.
Declining is part of routing rather than a separate guardrail layer. Left out: chat history (each
question stands alone, and the UI says so), follow-up questions, an eval suite, a vector database (the
policy is small enough to load in full), a real database, Docker, and auth, per the brief.

**How I'd evaluate it.** I'd build a golden set of about 50 questions with Finance: rankings, filters,
threshold boundaries (EUR 5,000.00 vs 5,000.01), compliance checks, and questions that must be declined
(payment status, approver identity). Expected answers come from independent calculations. I'd score
four things separately: route accuracy, tool-parameter accuracy, figure accuracy, and citation
precision and recall. Hallucination has two layers. The runtime check catches any figure, invoice id or
clause absent from the evidence, and its rejection rate is itself a metric. It can't catch a real
number used wrongly, such as the wrong vendor's total, so I'd add sampled analyst review and a judge
that checks each claim against its evidence. Prompt or model changes must pass this in CI, and adversarial
prompts should be included. Thumbs-down feedback from analysts feeds new cases.

**What production would need.**
- *Data:* a governed warehouse or ERP feed in place of CSVs, with versioned ingestion and data-quality
  checks; a real FX table; role, requester, payment and credit-note fields so that `cannot_verify` can
  become real checks; and the Exception Register.
- *Audit (§8.1, §8.2):* every answer needs to be reproducible, so log the user, question, plan, data and
  policy versions, prompt and model versions, rows used and answer to immutable storage, retained for 10
  years. The local JSONL file here shows the shape only. Validate the pipeline under internal controls
  testing, and make clear that this is decision support, not the system of record or an approval.
- *Access control:* SSO, with row-level permissions by entity and cost center enforced inside the tools,
  not in prompts. Approved data-processing terms with the LLM vendor, with no training on the data.
- *Scale and cost for 200 users:* stateless API replicas, a managed database, rate limits, per-user
  quotas and alerts. Each question makes at least two LLM calls, so use prompt caching for the policy,
  a cheaper model for routing, and cached results for repeated questions. Track cost per answer, latency,
  rejection rate and provider outages.

## Time and next steps

**Time:** about 5.5 hours in total. Roughly 4 hours went on the build: the data and policy layer
first, then the plan → tools → compose → check pipeline, then the UI. The last 1.5 hours went on
testing against independent calculations, fixing wrong answers that turned up, UI clean-up, and
checking the submission against the brief. Most of the time went into the data decisions above (FX,
credit notes, `cannot_verify`) rather than into the LLM calls. That was deliberate: in a
controls setting, the data semantics are where answers go wrong. How AI tools were used, with the
prompts, is in [AI_USAGE.md](AI_USAGE.md).

**Next:** run the prompts on a live model and tune them with a golden set; fetch daily FX rates and
check the rankings; add follow-up questions; and ask Finance to confirm the open interpretations, such as
non-publishing FX days and whether a credit note's approval band should use its absolute value (assumed).
